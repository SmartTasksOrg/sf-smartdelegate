# Threat model

Build 0.3.0. Scope: the Python reference (`src/sf_smartdelegate`) with its proxies
and bridges. Test names are in [`tests/`](../tests); "vectors" are the files in
[`spec/conformance/vectors`](../spec/conformance/vectors), which all six engines pass. The other
engines are covered only as far as threat 37 says. Where there is no control,
the row says so.

No part of this has had an independent security review.

## Assets

1. Data in upstream systems, at field granularity.
2. The ability to act (write, spend) in upstream systems.
3. Upstream credentials, held by the proxies.
4. The signing key, the admin key and the pep key.
5. The policy bundle: `policies.json`, `entities.json`, `catalog.json` and `roles.json`. `roles.json` says who holds each role and the most a token under it may carry.
6. The mapping files of the bridges: `cloud_map.json` (which cloud permission a SmartDelegate permission stands for), `group_map.json` and the claims rule (which directory group is which SmartDelegate group), and `idp.group_map` in the engine configuration.
7. The credential a directory sync uses to read the identity provider.
8. Cloud credentials made from a token (AWS session, down-scoped Google token, Azure On-Behalf-Of token).
9. The audit log.

## Trust assumptions

- The host running the engine, daemon and proxies is trusted, including its filesystem (state directory, bundle, signing key, configuration).
- Enforcement points are trusted to describe the call truthfully (`resource.attrs`, `context`).
- The OIDC provider is trusted to identify users, and, when `idp.groups_claim` is set or a directory is synced, to say which groups they are in.
- **Whoever holds the admin key, or calls the engine in-process, is trusted to state the user and the user's groups.** `issue_token` with `user` and `groups` is checked against nothing. Only a component that has itself verified the human's sign-in may make that call: a token service or back end, never an agent and never an enforcement point (those get the pep key).
- The job that runs a directory sync is trusted like an administrator: it rewrites `entities.json`, and with `--revoke` it holds the admin key.
- The mapping files (asset 6) are trusted input. The bundle signature does not cover them.
- The agent, the model, tool results, MCP servers and upstream responses are **not** trusted.

## Threats: agents, tokens, policy, proxies, audit

| # | Threat | What the system does | Test | What it does not do |
|---|---|---|---|---|
| 1 | Prompt-injected agent calls a tool it should not, or on a record it should not | Capability in the token, then policy; default deny for unmapped tools and routes | vectors `05_guards`; `McpProxy.test_unmapped_tool_is_denied_without_reaching_the_server`; `HttpProxy.test_no_token_bad_token_no_route` | Within what the token and policy allow, an injected agent can still act. Keep capabilities per task |
| 2 | Agent exfiltrates fields by reading more than the task needs | Field default deny, labels, mask before the model context | vectors `03_fields`; proxy masking tests | Permitted free-text fields can contain anything |
| 3 | Agent writes fields it may not write | Strict input check; request never forwarded | `test_write_with_a_forbidden_field_never_reaches_the_upstream` | |
| 4 | Agent spends beyond its authority, or splits spend across sub-agents | Budget charged against every token in the chain | vectors `04_spend_limits_approval`; `test_spend_is_shared_between_processes` | The ledger is per state directory. The budget is per token: a human who starts several agents gets one budget per token (threat 23) |
| 5 | Sub-agent tries to widen its token | Narrowing check at exchange; delegation policy; depth limit; the role cannot be changed | vectors `02_delegation`; `06_roles` "sub-agents inherit the role and cannot change it" | |
| 6 | Agent claims to act for another user | Identity only from the signed token; `context.iam` rejected | vectors `05_guards` "the caller cannot inject identity or malformed context"; `test_altered_token_payload_is_denied` | Admin-key issuance trusts the caller's stated user (threat 25) |
| 7 | Stolen capability token | Short lifetime, narrow capability, revocation of the token and its descendants, revocation of all of a user's tokens | vectors `01_tokens`, `02_delegation`, `10_offboarding` | Bearer token: usable until expiry or revocation. No proof-of-possession. A verify-only engine with its own state does not see a revocation |
| 8 | Forged or altered token (`alg: none`, payload edit, unknown key, wrong issuer, loose base64url, malformed `role` or `grp`) | EdDSA only; key id must be known; issuer and audience checked; strict base64url; claim types checked | `Keys` tests; `Strictness.test_base64url_is_strict`, `test_anc_must_be_an_array_of_strings`; matrix check c | |
| 9 | Agent bypasses enforcement and calls the upstream directly | Upstream credential held only by the proxy | `test_agent_cannot_reach_the_upstream_directly` | Depends entirely on deployment: network egress and secret placement are outside this software |
| 10 | Path or query tricks make the proxy authorise one resource and fetch another | Path parameters restricted to safe characters; only listed query parameters forwarded; no redirects followed | `test_path_tricks_and_unlisted_query_parameters_are_refused` | Upstream-specific parsing quirks beyond these |
| 11 | Compromised or careless MCP server leaks data through side channels (`_meta`, log notifications, error text, resources) | Result reduced to checked members; notifications and unlisted methods blocked; error details withheld | `McpProxy` tests | Tested against a stand-in server only |
| 12 | Upstream returns unparseable or unexpected data | Non-JSON withheld; unlisted fields dropped; error bodies withheld | `test_non_json_upstream_response_is_withheld`, `test_upstream_error_body_is_withheld` | |
| 13 | Tampered policy bundle, `roles.json` included | Ed25519 signature over the hashes of `policies.json`, `entities.json`, `catalog.json` and `roles.json`, required when a public key is configured; a failed reload keeps the old bundle | `SignedBundles` tests; matrix check d (a `roles.json` edited after signing is `bundle_signature` in every engine) | Signing is off unless `bundle_public_key` is configured |
| 13a | Policy source edited without recompiling, so reviewers read one policy and the engine runs another | `policies.json` records each source's hash; mismatch refuses the bundle | `test_source_edited_without_recompiling_is_refused` | A hand-edited `policies.json` is caught only by the signature and by review |
| 13b | An engine evaluates a policy differently from Cedar | Evaluation cases with real Cedar's answers; constructs outside the subset refused at load | `test_cedar_eval`, `test_cedar_outside_the_subset_is_refused_at_load` | Only what the 95 cases cover |
| 14 | Tampered audit log | Hash chain; records split at `\n` only | `Audit.test_edit_delete_and_reorder_are_detected`; `Strictness.test_audit_lines_end_at_newline_only`; matrix check e | Truncation of the tail and full re-forgery need an external anchor |
| 15 | Audit log leaks the data it protects | Field names only; no values; no tokens | `Audit.test_log_holds_field_names_not_values` | |
| 16 | Failure opens access (bad state file, full disk, daemon down, policy error, files that are not UTF-8) | Fail closed | `test_corrupt_state_file_fails_closed`, `test_unwritable_audit_log_fails_closed`, `Strictness.test_files_that_are_not_utf8`, the clients' "unreachable daemon" tests, vector "an erroring forbid policy denies" | |
| 17 | A user approves their own agent's held request | Self-approval refused; approver must be permitted by policy; approval bound to the exact request, single use | vectors `04_spend_limits_approval` (approval cases) | The approver's identity is asserted by the admin-key holder. The approver's groups are read from `entities.json`, never from live membership |
| 18 | Cross-tenant access | Tenant claim must equal the resource's tenant | vector "tenant isolation" | Only when the enforcement point supplies the resource's tenant |
| 19 | Theft of the signing key or the admin key | Signing key file mode 0600 on Unix; keys compared in constant time; the daemon refuses keys under 16 characters | none | No HSM/KMS integration, no key rotation procedure. The admin key is one static secret for issuing for any user, revoking, approving and reloading (threats 25, 35) |
| 20 | Denial of service against the daemon or proxies | Body size caps | none | Small synchronous servers; not hardened |
| 21 | Compromise of the host | none | none | Out of scope: the host is trusted |
| 21a | A test switch left on in production: `allow_test_clock` lets any caller set the clock with `now` (expiry, revocation cut-offs); `trust_caller_chain` accepts a caller-stated user, role and groups with no token and no ceiling | Both are off by default | `test_test_clock_is_ignored_unless_enabled`, `test_caller_chain_is_only_trusted_when_configured` | Nothing warns when either is on. `sf-smartdelegate info` does not show them |

## Threats: roles, membership, bridges, ports

| # | Threat | What the system does | Test | What it does not do |
|---|---|---|---|---|
| 22 | A human, or an agent asking on their behalf, gets a token for a role the human does not hold, or for more than the role allows | The human must hold the role at issuance. A requested capability must be narrower than the role's `cap`; the role's deny lists are added to it. `tasks`, `agents` and `max_ttl` of the role are enforced. Unknown role is an error | vectors `06_roles` (13 cases), `07_require_role` | A token issued **without** a role is bounded only by the requested capability and the delegation policy, unless the engine has `require_role`. With `require_role` off, roles are opt-in per request |
| 23 | A human multiplies a role's budget by starting many agents | none | none | Each token has its own budget. There is no budget per human across tokens. A `@rate_limit` counts per policy, agent and user, in memory, per process |
| 24 | `roles.json` is edited to widen a role, or a misspelt key silently loosens one | `roles.json` is part of the bundle version and of the signature (threat 13). An unknown key, a wrong type or a wrong top level fails the bundle load (`roles_parse`); a failed reload keeps the old bundle | matrix check d. Malformed `roles.json` documents are not tested in `tests/`; the Java and Go harnesses send them to the reference and compare verdicts | Without a required signature, whoever can write the bundle directory sets the ceilings. A wider `cap` that is well-formed is caught only by review |
| 25 | A caller with the admin key supplies `groups` (or `user`) that are not true | none: this input is trusted (see Trust assumptions). The engine only normalises it: groups that `entities.json` does not define are dropped, and it then replaces the stored membership of that user for the token. With an `id_token` in the request, `groups` and `user` from the caller are ignored | vectors `06_roles` "group claims are normalised…", `09_oidc_groups` "groups passed by the caller are ignored when an ID token is presented" | The holder of the admin key can obtain any role for any user name, up to the role's ceiling and the delegation policy, including for a user `entities.json` does not list. The audit record of the issuance holds user, role and capability, but not the groups that were supplied or who supplied them |
| 26 | Replay of an ID token. (a) Someone who obtains a human's ID token uses it. (b) An ID token issued before the human lost a group is used afterwards | Signature against the configured JWKS, issuer, audience, `azp`, `exp`, `nbf` when present, and the user's revoke cut-off against `iat`. Identity comes from the token alone | vectors `08_oidc`, `09_oidc_groups`, `12_oidc_nested_claim`; `Oidc` tests; `live/idp` against a real Keycloak | (a) `POST /v1/token` with an `id_token` needs no key, and an ID token can be used any number of times until it expires: there is no nonce, no `jti` record, no maximum age, no binding to a client. Anyone who holds the ID token can obtain capability tokens for that human. (b) The old group list is accepted until the ID token expires, and it **replaces** the stored membership, so it also overrides a sync that already removed the human. Since the first run against a real Keycloak, a revoke-by-user closes this from the moment of the revoke: an ID token whose `iat` is at or before the user's cut-off is refused (`id_token_invalid`; vectors `08_oidc`, `live/idp`), and `azp` must name this client. What remains is the time between the removal at the provider and the sync that revokes: the old ID token works for the rest of its lifetime. Keep ID-token lifetimes short |
| 27 | Group-claim overage: the provider leaves the groups out of the ID token (Entra ID above 200 groups), or sends only some of them | Engine path (`idp.groups_claim`): a missing claim is membership in nothing, so a role request fails with `role_not_held`. Bridge path (`claims` preset `entra`): raises `claims_overage` instead of returning an empty list | vectors `09_oidc_groups` (an ID token without the claim; unmapped and unknown groups dropped); `Claims.test_entra_overage` | Dropping groups is safe only for rules that **grant** on membership. Live membership replaces the stored one, so a `forbid` (or an `unless`) that depends on the human being in a group stops applying when that group is missing from the claim, not in `idp.group_map`, or not defined in `entities.json`. The engine path cannot tell an overage from "no groups" and has no call to fetch the full list |
| 28 | A compromised or wrong directory sync **adds** membership (the directory, the sync job, `group_map.json` or the response in transit is wrong) | TLS verification on, https only except loopback, no redirect to another host. The new `entities.json` is loaded with the engine's loader before it replaces the old one. With `--group-map`, groups not in the map are dropped | `UrllibTransport.test_redirects`, `HttpHelpers.test_plain_http_is_refused_except_loopback`, `Adapters.test_a_next_link_to_another_host_is_refused`, `Entities.test_atomic_write_on_failure` | Nothing checks that added membership is true. A sync job that re-signs the bundle itself makes the signature worthless against this threat. TLS was not exercised by any test (all tests use http on loopback). No adapter has been run against the real service |
| 29 | A compromised or broken sync **removes** membership, or revokes users (`--revoke`), to stop work | Removal guard: nothing is written when more than 30% (configurable) of users would disappear or lose all groups. A truncated listing, a repeated or foreign `next` link, an HTTP error or malformed page aborts the sync with nothing written | `Entities.test_removal_guard`, `Adapters.test_truncated_listings_raise`, `test_http_errors_and_malformed_pages_raise`, `test_a_looping_next_page_stops` | Below the guard's fraction the change is written, and with `--revoke` every affected user loses all live tokens. `--force` turns the guard off |
| 30 | A stale sync: the job stops (expired credential, tripped guard, missing re-sign step) and a removed human keeps the membership on disk | `entities.sync.json` records `synced_at`. A role's `max_ttl` bounds tokens already issued | `Entities.test_sidecar_and_dry_run` | Nothing reads `synced_at` or alerts. Issuance from stale membership continues for as long as the sync is down. A running engine also keeps the `entities.json` it loaded until `reload`, and an engine that requires a signature refuses the new file until it is re-signed |
| 31 | Theft or over-privilege of the sync credential | It is read from an environment variable named by the caller, never from a file, never written to `entities.sync.json`, an error message or the output. [BRIDGES.md](BRIDGES.md) lists the read-only permission each adapter needs | `HttpHelpers.test_secret_from_env`, `test_errors_carry_no_secret_and_no_body`, `Adapters.test_wrong_or_missing_credential` | The permission names in that list are unverified. A read-only directory credential still exposes every user and group. A sync with `--revoke` or `--daemon-url` also carries the admin key in its environment |
| 32 | The down-scoped cloud credential outlives the token, or the revocation of the token | AWS: `DurationSeconds` is the time the token has left, capped by `max_duration`. Session tags name the user, agent, role, task and token id for CloudTrail | `Aws.test_assume_role_request` | AWS's minimum is 900 seconds: a token with less time left gets a session that outlives it by up to the difference. No revocation (by token or by user) reaches a cloud credential already issued, on any of the three clouds. The Google and Azure helpers do not set a lifetime from the token |
| 33 | The down-scoped credential is wider than the token (a wrong line in `cloud_map.json`, or a wrong assumption about the cloud) | What does not map is not granted; AWS gets an explicit deny-all policy rather than none. An unknown key in the map is an error. Ids containing IAM wildcards are not granted. `--unverified` tokens cannot be turned into an AssumeRole request | `Generators.test_aws_policy_is_never_wider_than_the_cap`, `test_gcp_boundary_is_never_wider_than_the_cap`, `test_azure_scopes_are_never_wider_than_the_cap` (300 seeded random cases each, judged by an evaluator in the test file), `Aws.test_unmapped_is_default_deny`, `test_ids_with_iam_wildcards_are_not_granted` | The evaluator in the tests is not IAM. No cloud has evaluated a generated policy, boundary or scope list. [BRIDGES.md](BRIDGES.md) "UNVERIFIED" marks the assumptions that would leave access wider if wrong. A cloud credential never carries `deny_labels`, `deny_fields` or `budget`. Azure has no per-token policy at all; a Google boundary covers Cloud Storage only |
| 34 | A role ceiling computed from cloud permissions is wrong or old | `cap_role` can lower a role's `cap`, never widen it. A missing result is not "allowed" | `Ceiling.test_cap_role_never_widens`, `test_cap_role_random_never_wider_than_the_file`, `test_overlapping_rules_must_all_be_allowed` | A ceiling is a snapshot of the simulation it came from. Three of the "wider" items in BRIDGES.md concern ceilings |
| 35 | Revoke-by-user as a denial-of-service lever | It needs the admin key (`POST /v1/admin/revoke`), or a sync run with `--revoke`. Every call writes a `user_revoked` audit record with `by` | vectors `10_offboarding` "revoking a user is recorded in the audit log"; `Cli.test_sync_revoke_and_reload_through_a_daemon` (wrong admin key refused) | Whoever holds the admin key can end every live token of any user, as often as they like: no rate limit, no second approver, no undo. It is a cut-off, so the user's agents can ask again, and are cut again. `by` is whatever the caller wrote. With `allow_test_clock` on, `now` can set the cut-off in the future, which is a ban until then (threat 21a) |
| 36 | Offboarding does not reach everything | `revoke {"user"}` denies every token of that user issued up to the call, sub-agent tokens included, on the next decision of every engine sharing the state directory | vectors `10_offboarding`; `Entities.test_revoke_changed_ends_tokens_of_removed_and_shrunk_users_only`. Across ports on one state directory: the Go and PHP suites, each with the reference (the matrix checks revocation by token there, not by user) | Not reached: a verify-only engine with its own state; cloud credentials already issued; tokens issued after the call (the human must also have lost the membership at the source, and the engine must have reloaded). The user is matched by the exact string in the token's `sub`: a directory id and a login name for the same person are two users |
| 37 | The engines differ, so one accepts what another refuses (issuer in one language, verifier in another; or a bundle that loads in one and not in the other) | One specification; 95 evaluation cases with Cedar's answers; 78 conformance cases (327 steps); the "Strictness (0.3)" rules, each with a test in every port; the cross-port matrix, in which every port's role token, sub-agent token, tampered token, signed bundle and audit log is checked by every other port (158 checks, 0 failed, on 2026-10-05) | `ports/conformance/run.sh`, `ports/conformance/matrix.py`, each port's own suite | Behaviour no case exercises can differ. Each port's README lists known differences from the reference (integers beyond 64 bits, nesting depth, daemon edge cases, message texts). The matrix runs one fixed scenario per pair; it is not a differential fuzzer. Node.js and Java use their own state-directory locks: sharing a directory between them and another port can corrupt state and the audit chain |
